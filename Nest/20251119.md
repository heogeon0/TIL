### 1. NestJS 기초 개념 (2025-11-10)

**NestJS의 핵심 특징**

- **TypeScript 기반**: Express를 기반으로 만들어졌으며, TypeScript를 기본으로 사용하여 강력한 타입 안정성 제공
- **모듈러 아키텍처**: 기능별로 모듈을 분리하여 확장 가능한 구조
- **DI (Dependency Injection)**: 의존성 주입 패턴을 프레임워크 레벨에서 지원
- **AOP (Aspect Oriented Programming)**: Interceptor, Guard, Pipe 등을 통한 관점 지향 프로그래밍 지원
- **데코레이터 패턴**: `@Controller`, `@Injectable`, `@Module` 등 데코레이터를 활용한 직관적인 코드 작성
- **테스트 친화적**: Jest를 기본 테스트 프레임워크로 채택
- **마이크로서비스 지원**: TCP, Redis, MQTT, gRPC 등 다양한 전송 계층 지원

**NestJS를 선택하는 이유**
- 대규모 애플리케이션을 위한 체계적인 구조
- 타입 안정성으로 런타임 에러 감소
- 테스트와 유지보수가 용이한 DI 패턴
- Angular와 유사한 구조로 학습 시너지

### 2. Express vs NestJS (2025-11-11)

**주요 차이점 비교**

| 구분 | Express | NestJS |
|------|---------|--------|
| **구조** | 미니멀리스트, 자유로운 구조 | 모듈 기반 체계적 아키텍처 |
| **타입 시스템** | JavaScript 기본 | TypeScript 기본 |
| **의존성 주입** | 없음 (직접 구현 필요) | 내장 DI 컨테이너 제공 |
| **코드 스타일** | 미들웨어 중심 선형 구조 | 데코레이터 기반 선언적 구조 |
| **확장성** | 별도 설계 필요 | 모듈화 및 확장성 고려된 설계 |
| **학습 곡선** | 낮음 | 중간 (장기적 이점) |

**Express 미들웨어 핵심 개념**

```javascript
// 미들웨어 기본 구조
function middleware(req, res, next) {
  // 요청 전처리
  console.log('미들웨어 실행');
  next(); // 다음 미들웨어로 제어권 전달
}

// 인증 미들웨어 예제
const authMiddleware = (req, res, next) => {
  const token = req.headers.authorization;
  if (!token) {
    return res.status(401).json({ error: '인증 필요' });
  }
  req.user = { id: 1, name: 'John' };
  next();
};
```

**미들웨어의 역할**
- 요청 전처리 (데이터 검증, 파싱)
- 인증/인가 (사용자 권한 확인)
- 로깅 (요청/응답 기록)
- 에러 처리

### 3. Controller와 HMR (2025-11-12)

**Hot Module Replacement (HMR)**
- 코드 수정 시 서버를 재시작하지 않고 변경사항을 즉시 반영
- 개발 속도 향상
- Webpack의 HMR 기능 활용

**Controller 기본 개념**

```typescript
import { Controller, Get, Post, Body, Param } from '@nestjs/common';

@Controller('users')  // /users 경로
export class UsersController {
  @Get()  // GET /users
  findAll() {
    return '모든 사용자 조회';
  }

  @Get(':id')  // GET /users/:id
  findOne(@Param('id') id: string) {
    return `사용자 ${id} 조회`;
  }

  @Post()  // POST /users
  create(@Body() userData: any) {
    return `사용자 생성`;
  }
}
```

**주요 데코레이터**
- `@Controller()`: 컨트롤러 클래스 정의
- `@Get()`, `@Post()`, `@Put()`, `@Delete()`: HTTP 메서드 매핑
- `@Param()`: URL 파라미터 추출
- `@Body()`: 요청 본문 추출
- `@Query()`: 쿼리 스트링 추출

### 4. Service와 DI (2025-11-13)

**관심사의 분리 원칙**

| 역할 | Controller | Service |
|------|------------|---------|
| **책임** | 요청/응답 처리 | 비즈니스 로직 |
| **의존성** | HTTP에 의존 | HTTP 독립적 |
| **재사용성** | 낮음 | 높음 (여러 컨트롤러에서 사용) |
| **테스트** | 통합 테스트 | 단위 테스트 용이 |

**의존성 주입 (DI) 구현**

```typescript
// 1. Service 정의
@Injectable()
export class UserService {
  findById(id: number) {
    return this.users.find(user => user.id === id);
  }
}

// 2. Controller에서 주입받기
@Controller('users')
export class UserController {
  constructor(private userService: UserService) {}

  @Get(':id')
  getUser(@Param('id') id: number) {
    return this.userService.findById(id);
  }
}

// 3. Module에 등록
@Module({
  controllers: [UserController],
  providers: [UserService],
})
export class AppModule {}
```

**DI의 장점**
- 결합도 감소 (느슨한 결합)
- 테스트 용이 (Mock 객체 주입)
- 코드 재사용성 증가
- 싱글톤 패턴 자동 관리

**환경변수 관리 (ConfigModule)**

```typescript
// 설정
@Module({
  imports: [
    ConfigModule.forRoot({
      isGlobal: true,
      envFilePath: '.env',
    }),
  ],
})

// 사용
@Injectable()
export class AppService {
  constructor(private configService: ConfigService) {}

  getDatabaseHost(): string {
    return this.configService.get<string>('DB_HOST');
  }
}
```

**Morgan 로깅 미들웨어**

```typescript
@Injectable()
export class LoggerMiddleware implements NestMiddleware {
  private logger = morgan('dev');

  use(req: Request, res: Response, next: NextFunction) {
    this.logger(req, res, next);
  }
}
```

**implements 키워드**
- TypeScript에서 클래스가 특정 인터페이스를 구현하도록 강제
- 코드 일관성과 타입 안정성 보장
- 컴파일 타임에 필수 메서드 체크

### 5. 파일 컨벤션, CLI, Swagger (2025-11-17)

**NestJS 파일 명명 규칙**

├── users/
│   ├── users.controller.ts      # HTTP 요청/응답 처리
│   ├── users.service.ts         # 비즈니스 로직
│   ├── users.module.ts          # 모듈 정의
│   ├── users.entity.ts          # 데이터베이스 엔티티

│   │   └── update-user.dto.ts   # 수정 요청 DTO

**파일 확장자 규칙**

- `*.entity.ts`: 엔티티

- `*.interceptor.ts`: 인터셉터

### 6. 커스텀 데코레이터, 인터셉터, AOP (2025-11-18)

**커스텀 파라미터 데코레이터**

```typescript
// 데코레이터 정의
export const CurrentUser = createParamDecorator(
  (data: unknown, ctx: ExecutionContext) => {
    const request = ctx.switchToHttp().getRequest();
    return request.user;
  },
);

// 사용
@Get('profile')
getProfile(@CurrentUser() user: User) {
  return user;
}
```

**복합 데코레이터 (여러 데코레이터 묶기)**

```typescript
export function Auth(...roles: string[]) {
  return applyDecorators(
    UseGuards(AuthGuard, RolesGuard),
    ApiBearerAuth(),
    ApiUnauthorizedResponse({ description: '인증 실패' }),
  );
}

// 사용
@Auth('admin')
@Get('admin')
adminOnly() {
  return '관리자 전용';
}
```

**인터셉터 (Interceptor)**

```typescript
// 응답 변환 인터셉터
@Injectable()
export class TransformInterceptor<T> implements NestInterceptor<T, Response<T>> {
  intercept(context: ExecutionContext, next: CallHandler): Observable<Response<T>> {
    return next.handle().pipe(
      map(data => ({
        success: true,
        data,
        timestamp: new Date().toISOString(),
      })),
    );
  }
}

// 성능 측정 인터셉터
@Injectable()
export class PerformanceInterceptor implements NestInterceptor {
  intercept(context: ExecutionContext, next: CallHandler): Observable<any> {
    const start = Date.now();
    return next.handle().pipe(
      tap(() => {
        const duration = Date.now() - start;
        console.log(`실행 시간: ${duration}ms`);
      }),
    );
  }
}
```

**인터셉터 적용 레벨**
- 메서드 레벨: `@UseInterceptors(LoggingInterceptor)`
- 컨트롤러 레벨: 컨트롤러 클래스 위에 적용
- 전역 레벨: `app.useGlobalInterceptors(new LoggingInterceptor())`

**AOP (Aspect-Oriented Programming)**

AOP는 비즈니스 로직과 부가 기능(횡단 관심사)을 분리하는 프로그래밍 패러다임입니다.

**NestJS의 AOP 구현 요소**

| 요소 | 역할 | 예시 |
|------|------|------|
| **Middleware** | 라우터 핸들러 전에 실행 | 로깅, CORS |
| **Guard** | 요청 허용 여부 결정 | 인증, 권한 체크 |
| **Interceptor** | 요청/응답 변환, 확장 | 로깅, 캐싱, 응답 변환 |
| **Pipe** | 데이터 검증, 변환 | 유효성 검증, 타입 변환 |
| **Exception Filter** | 예외 처리 | 에러 응답 포맷 |

**실행 순서**
```
Request
  ↓
Middleware
  ↓
Guard
  ↓
Interceptor (before)
  ↓
Pipe
  ↓
Controller/Service
  ↓
Interceptor (after)
  ↓
Exception Filter (에러 발생 시)
  ↓
Response
```

**AOP의 장점**

```typescript
// ❌ AOP 없이 - 비즈니스 로직과 부가 기능이 섞임
@Get()
findAll() {
  console.log('로깅');
  if (!user) throw new Error(); // 인증
  const start = Date.now(); // 성능 측정
  const result = this.service.findAll(); // 핵심 로직
  console.log(Date.now() - start);
  return result;
}

// ✅ AOP 적용 - 핵심 로직만 남음
@UseGuards(AuthGuard)
@UseInterceptors(LoggingInterceptor, PerformanceInterceptor)
@Get()
findAll() {
  return this.service.findAll(); // 핵심 비즈니스 로직만
}
```

**핵심 개념**:

**NestJS의 3대 핵심 원칙**
1. **모듈화 (Modularization)**: 기능별로 모듈을 분리하여 확장 가능한 구조
2. **의존성 주입 (DI)**: 결합도를 낮추고 테스트 용이성 증가
3. **관점 지향 프로그래밍 (AOP)**: 횡단 관심사를 분리하여 코드 중복 제거

**아키텍처 레이어**
```
Client Request
    ↓
Controller (요청/응답 처리)
    ↓
Service (비즈니스 로직)
    ↓
Repository/Entity (데이터 접근)
    ↓
Database
```

**데코레이터 기반 선언적 프로그래밍**
- Express의 명령형 스타일보다 코드 의도가 명확
- 메타데이터 기반으로 프레임워크가 자동 처리
- 보일러플레이트 코드 감소

**예제 코드**:
```typescript
// NestJS 종합 예제 - 모든 개념 통합

// 1. Entity
@Entity()
export class User {
  @PrimaryGeneratedColumn()
  id: number;

  @Column()
  email: string;

  @Column()
  name: string;
}

// 2. DTO
export class CreateUserDto {
  @ApiProperty({ example: 'john@example.com' })
  @IsEmail()
  email: string;

  @ApiProperty({ example: 'John Doe' })
  @IsString()
  name: string;
}

// 3. Service (비즈니스 로직)
@Injectable()
export class UsersService {
  constructor(
    @InjectRepository(User)
    private usersRepository: Repository<User>,
  ) {}

  async create(createUserDto: CreateUserDto): Promise<User> {
    const user = this.usersRepository.create(createUserDto);
    return this.usersRepository.save(user);
  }

  async findAll(): Promise<User[]> {
    return this.usersRepository.find();
  }
}

// 4. Controller (요청/응답)
@ApiTags('users')
@UseGuards(AuthGuard)
@UseInterceptors(TransformInterceptor)
@Controller('users')
export class UsersController {
  constructor(private readonly usersService: UsersService) {}

  @Post()
  @ApiOperation({ summary: '사용자 생성' })
  @ApiResponse({ status: 201, description: '생성 성공' })
  create(@Body() createUserDto: CreateUserDto) {
    return this.usersService.create(createUserDto);
  }

  @Get()
  @ApiOperation({ summary: '전체 사용자 조회' })
  findAll(@CurrentUser() user: User) {
    return this.usersService.findAll();
  }
}

// 5. Module (의존성 묶음)
@Module({
  imports: [TypeOrmModule.forFeature([User])],
  controllers: [UsersController],
  providers: [UsersService],
  exports: [UsersService],
})
export class UsersModule {}
```

**결과**:
- **타입 안정성**: TypeScript로 런타임 에러 사전 방지
- **유지보수성**: 관심사 분리로 코드 수정 시 영향 범위 최소화
- **테스트 용이성**: DI로 Mock 객체 주입 간편
- **확장성**: 모듈 기반 구조로 기능 추가 용이
- **생산성**: CLI와 데코레이터로 보일러플레이트 코드 자동 생성
- **문서화**: Swagger 자동 문서화로 프론트엔드 협업 효율 증가

## 💡 인사이트 & 깨달음

- **Express → NestJS 전환의 핵심 가치**: 자유도를 일부 포기하는 대신, 체계적인 구조와 타입 안정성을 얻음. 대규모 프로젝트일수록 NestJS의 장점이 극대화됨
- **DI의 진정한 의미**: 단순히 `new`를 안 쓰는 것이 아니라, 객체 간 결합도를 낮춰 테스트와 유지보수를 용이하게 만드는 설계 철학
- **AOP의 강력함**: 로깅, 인증, 성능 측정 등 횡단 관심사를 비즈니스 로직에서 분리하면, 코드가 본질적인 목적에만 집중할 수 있음 (단일 책임 원칙)
- **데코레이터 = 메타프로그래밍**: 코드에 대한 코드를 작성하여, 프레임워크가 런타임에 적절한 동작을 수행하도록 지시
- **CLI의 가치**: 단순 편의성이 아니라, 팀 전체가 동일한 코드 구조를 유지하게 만드는 컨벤션 강제 도구
- **Swagger의 ROI**: 초기 데코레이터 추가는 번거롭지만, API 문서가 코드와 자동 동기화되므로 장기적으로 엄청난 시간 절약
- **관심사의 분리가 곧 확장성**: Controller는 HTTP만, Service는 로직만, Repository는 데이터만 담당. 각자의 역할이 명확할수록 변경에 강한 코드
- **TypeScript + 데코레이터 조합**: Java의 Spring과 유사하지만, JavaScript 생태계의 유연함을 유지. 두 세계의 장점을 결합

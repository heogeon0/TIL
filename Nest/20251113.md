#### 상세 내용

- **컨트롤러와 서비스를 분리하는 이유 (관심사의 분리)**

	**역할 구분**
	- **서비스(Service)**: 비즈니스 로직만 담당
		- 요청(req), 응답(res)에 대해 알지 못함
		- 순수하게 데이터 처리와 비즈니스 로직만 실행
		- 결과 값만 반환
	- **컨트롤러(Controller)**: 요청/응답 처리
		- HTTP 요청(`req`)과 응답(`res`) 관리
		- 서비스를 호출하고 결과를 클라이언트에 전달
		- NestJS에서는 return만 하면 자동으로 response 생성

	**분리의 장점**
	```typescript
	// ✅ 올바른 분리
	// user.service.ts - 비즈니스 로직만
	@Injectable()
	export class UserService {
	  findById(id: number) {
	    // HTTP와 무관한 순수 로직
	    return this.users.find(user => user.id === id);
	  }
	}

	// user.controller.ts - 요청/응답 처리
	@Controller('users')
	export class UserController {
	  constructor(private userService: UserService) {}

	  @Get(':id')
	  async getUser(@Param('id') id: number) {
	    return this.userService.findById(id); // 자동으로 JSON 응답
	  }
	}
	```

	**1. 테스트 용이성**
	```typescript
	// 서비스만 독립적으로 테스트 가능 (HTTP 없이)
	describe('UserService', () => {
	  it('should find user by id', () => {
	    const user = userService.findById(1);
	    expect(user.id).toBe(1);
	  });
	});
	```

	**2. 재사용성 증가**

	```typescript
	export class AdminUserController {
	  constructor(private userService: UserService) {} // 동일한 서비스 사용
	}

	export class ApiUserController {
	  constructor(private userService: UserService) {} // 동일한 서비스 사용
	}
	```

	- HTTP 처리 변경 시 컨트롤러만 수정

- **Morgan으로 요청 로깅**

	**설치**
	```bash
	npm install morgan
	npm install -D @types/morgan
	```

	**NestJS 미들웨어로 구현**
	```typescript
	// logger.middleware.ts
	import { Injectable, NestMiddleware } from '@nestjs/common';
	import { Request, Response, NextFunction } from 'express';
	import * as morgan from 'morgan';

	@Injectable()
	export class LoggerMiddleware implements NestMiddleware {
	  private logger = morgan('dev');

	  use(req: Request, res: Response, next: NextFunction) {
	    this.logger(req, res, next);
	  }
	}
	```

	**implements의 역할**
	- `NestMiddleware` 인터페이스를 구현하도록 강제
	- `use` 메서드를 반드시 구현해야 함
	- 컴파일 타임에 타입 체크

	**모듈에 적용**
	```typescript
	// app.module.ts
	import { Module, NestModule, MiddlewareConsumer } from '@nestjs/common';

	@Module({
	  imports: [],
	  controllers: [AppController],
	  providers: [AppService],
	})
	export class AppModule implements NestModule {
	  configure(consumer: MiddlewareConsumer) {
	    consumer
	      .apply(LoggerMiddleware)
	      .forRoutes('*'); // 모든 라우트에 적용
	  }
	}
	```

	**Context를 사용하는 이유**
	```typescript
	import { Logger } from '@nestjs/common';

	@Injectable()
	export class UserService {
	  private readonly logger = new Logger(UserService.name); // Context 지정

	  findAll() {
	    this.logger.log('Finding all users'); // [UserService] Finding all users
	    return this.users;
	  }
	}

	@Injectable()
	export class PostService {
	  private readonly logger = new Logger(PostService.name);

	  findAll() {
	    this.logger.log('Finding all posts'); // [PostService] Finding all posts
	    return this.posts;
	  }
	}
	```

	**Context의 장점**
	- 로그가 어느 클래스/모듈에서 발생했는지 명확히 구분
	- 디버깅 시 로그 추적이 용이
	- 실제 운영 환경에서 로그 필터링 가능

	**Morgan 포맷 옵션**
	```typescript
	morgan('combined')  // 상세한 로그 (프로덕션)
	morgan('dev')       // 개발용 컬러 로그
	morgan('tiny')      // 최소한의 로그
	morgan('common')    // 표준 Apache 로그
	```

**핵심 개념**:

**implements란?**
- TypeScript에서 **클래스가 특정 인터페이스를 구현하도록 강제**하는 키워드
- 인터페이스에 정의된 모든 속성과 메서드를 반드시 구현해야 함
- 코드의 일관성과 타입 안정성을 보장

**implements 사용 예제**
```typescript
// 인터페이스 정의
interface NestMiddleware {
  use(req: Request, res: Response, next: NextFunction): void;
}

// implements로 인터페이스 구현
export class LoggerMiddleware implements NestMiddleware {
  // use 메서드를 반드시 구현해야 함
  use(req: Request, res: Response, next: NextFunction) {
    console.log('Request...');
    next();
  }
}
```

**implements 사용 이유**
- 코드 일관성: 같은 인터페이스를 구현한 클래스들은 동일한 구조를 가짐
- 컴파일 타임 체크: 필수 메서드를 빠뜨리면 에러 발생
- 유지보수성: 어떤 메서드를 구현해야 하는지 명확함

### Injectable (의존성 주입 - DI)

**의존성 주입(Dependency Injection)이란?**
- 클래스가 필요한 객체를 직접 생성하지 않고, 외부에서 주입받는 디자인 패턴
- 객체 간의 결합도를 낮추고 테스트와 유지보수를 쉽게 함

**DI를 하는 이유**

**1. 결합도 감소**
```typescript
// ❌ DI 없이 - 강한 결합
class UserController {
  private userService = new UserService(); // 직접 생성
}

// ✅ DI 사용 - 느슨한 결합
class UserController {
  constructor(private userService: UserService) {} // 주입받음
}
```

**2. 테스트 용이성**
```typescript
// 테스트 시 Mock 객체를 쉽게 주입 가능
const mockUserService = { findAll: jest.fn() };
const controller = new UserController(mockUserService);
```

**3. 코드 재사용성**
- 같은 서비스를 여러 컨트롤러에서 공유 가능
- 싱글톤 패턴으로 메모리 효율적

**NestJS에서 DI 사용하기**

**1. Provider 등록**
```typescript
@Module({
  controllers: [UserController],
  providers: [UserService], // Provider로 등록
})
export class AppModule {}
```

**2. 클래스 방식 주입 (가장 일반적)**
```typescript
@Injectable()
export class UserService {
  findAll() {
    return ['user1', 'user2'];
  }
}

@Controller('users')
export class UserController {
  // 생성자에서 자동 주입
  constructor(private readonly userService: UserService) {}

  @Get()
  getUsers() {
    return this.userService.findAll();
  }
}
```

**3. Value 방식 주입**
```typescript
// app.module.ts
@Module({
  providers: [
    {
      provide: 'API_KEY',
      useValue: 'my-secret-key-123',
    },
  ],
})
export class AppModule {}

// 사용하는 곳
@Injectable()
export class ApiService {
  constructor(@Inject('API_KEY') private apiKey: string) {
    console.log(this.apiKey); // 'my-secret-key-123'
  }
}
```

**4. Factory 방식 주입 (동적 생성)**
```typescript
@Module({
  providers: [
    {
      provide: 'DATABASE_CONNECTION',
      useFactory: async () => {
        return await createConnection();
      },
    },
  ],
})
```

**DI의 장점 정리**
- **결합도 감소**: 클래스 간 독립성 증가
- **테스트 용이**: Mock 객체 주입으로 단위 테스트 쉬움
- **재사용성**: 동일한 인스턴스를 여러 곳에서 공유
- **유지보수**: 변경 사항이 다른 코드에 영향 최소화
- **싱글톤 관리**: NestJS가 자동으로 인스턴스 생명주기 관리
